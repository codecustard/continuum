Games that build on each other.

Continuum is an open standard on Sui. Any game can read another game's objects, attach its own data to them, and make new things from them, with lineage anyone can check. No permission or partnership needed.

Three rules. Nothing else.

A game follows the rules that apply to it. Field names, stats and everything else stay up to each game, so shared conventions can come from use instead of committees.

Open slots

Your object exposes uid_mut. Other games attach their data under a key struct only they can create, so no game can touch another's slot. Owners can lock an object to stop new slots.

public fun uid_mut(koi: &mut Koi): &mut UID {
    assert!(!koi.locked, ELocked);
    &mut koi.id
}

Verified provenance

Anything made from another object stores a record from derive. The source has to be in the same transaction, so the link can't be faked. Sources on other chains use claim and are marked unverified.

let from = provenance::derive(MyGame {}, &koi, ctx);
// from.is_verified() == true
// from.source_is<Koi>() == true

Manifest

Link a manifest from your package's record in Sui's Move Registry. It says what your fields mean, which types you make and read, and how your art and data are licensed.

package_info.set_metadata(
    "continuum.manifest",
    "https://…/manifest.json");

Left out on purpose: trust and anti-cheat, balance, shared stat names, economy. Each game decides what it trusts.

Why build on it

Start with players

Your game can open with objects people already own and care about, instead of an empty inventory.

Outlive your game

What players earn stays on chain in their wallets. The next game, or a remix of yours, can pick it up.

Players never see the chain

Social sign-in and sponsored gas mean no wallet popups during play. On-chain moments are rare and batched into one transaction.

Join at any level

Each level is optional and they stack. An existing Sui game can add them with a normal package upgrade.

  1. 0

    Read

    Do nothing. Read any object over RPC.

    Use other games' objects in yours.

  2. 1

    Manifest

    Publish a manifest and link it from your MVR record.

    Other builders can find you and know what your fields mean.

  3. 2

    Derive

    Use derive when you make things from others' objects.

    Verified lineage back to the source.

  4. 3

    Open slots

    Expose uid_mut with a lock flag.

    Other games can build on your objects.

A second game, in a few lines

A restaurant game cooks a dish from a koi and leaves a note on the koi itself. It never asked the koi game for anything.

Collections that don't know about Continuum work too: keep a record your game owns that points at the item through derive.

use continuum::provenance::{Self, Provenance};

public struct Tindahan has drop {}            // your witness
public struct FedSlot has copy, drop, store {}

public struct Dish has key, store {
    id: UID,
    from: Provenance,
}

public fun cook(koi: &mut Koi, ctx: &mut TxContext): Dish {
    // leave our own data on their object
    dynamic_field::add(koi.uid_mut(), FedSlot {}, 1u64);
    // make something new from it, with verified lineage
    let from = provenance::derive(Tindahan {}, koi, ctx);
    Dish { id: object::new(ctx), from }
}
